# Архитектура

Приложение сознательно небольшое: одна Activity, два экрана, четыре таблицы.
Ниже — как устроен код и почему приняты такие решения.

## Контекст и ограничения

- Android-only, офлайн, без аккаунтов и сети.
- Один мастер, десятки заказов, единицы фото на заказ.
- Телефоны уровня TECNO/Infinix, Android 7–15; слабый диск и мало RAM.
- Нужен предсказуемый APK без экзотических зависимостей.

Отсюда: нативный Kotlin, Compose, Room, минимум библиотек, никакого DI-фреймворка
и навигационной библиотеки.

## Слои

```
┌──────────────────────────────────────────────┐
│ ui/                                          │
│  OrdersScreen        OrderDetailScreen       │
│  OrdersViewModel     OrderDetailViewModel    │
│  Components, theme                           │
└───────────────┬──────────────────────────────┘
                │ состояние (StateFlow) и события
┌───────────────▼──────────────────────────────┐
│ data/                                        │
│  OrderRepository  ── единственная точка записи│
│  OrderDao (Flow)  AppDatabase  PhotoStore     │
└───────────────┬──────────────────────────────┘
                │ SQL / файлы
        ┌───────▼────────┐      ┌──────────────┐
        │ SQLite (Room)  │      │ files/photos │
        └────────────────┘      └──────────────┘
```

`domain/` — чистые функции и константы: статусы, типовые проверки, склонения,
формат дат, превью проблемы. Они не зависят от Android и покрыты JVM-тестами.

## Поток данных

### Список
`OrderDao.observeCards()` отдаёт `Flow<List<OrderCard>>`; вьюмодель объединяет его
с поиском и фильтром, кладёт в `StateFlow<OrdersUiState>`. Экран подписан через
`collectAsStateWithLifecycle()`.

Счётчики деталей и фото считаются в том же запросе подзапросами — без N+1 и без
второго источника истины.

### Карточка
Текстовые поля нельзя гонять в базу на каждое нажатие: курсор прыгает, диск
нагружается. Поэтому:

1. `OrderDetailViewModel` один раз читает заказ в `draft: StateFlow<OrderEntity?>`.
2. Каждое изменение обновляет черновик мгновенно (UI отзывчив).
3. Сохранение откладывается на 250 мс; повторная правка отменяет предыдущую задачу.
4. `flush()` вызывается при нажатии «назад», в `ON_STOP` и в `onDispose` композиции.
5. Сохранение идёт в `appScope` (`SupervisorJob + Dispatchers.IO`), а не в
   `viewModelScope`, чтобы не потерять последнюю правку при уничтожении экрана.

Чек-лист, запчасти и фото — дискретные действия: пишутся сразу и приходят обратно
через `Flow`. Поэтому они всегда отражают базу, а не черновик.

### Фото
1. `PhotoStore.newFile(orderId)` готовит путь в `files/photos`.
2. `FileProvider` отдаёт URI системной камере с правом записи только на этот файл.
3. После `RESULT_OK` файл проверяется на ненулевой размер и в базу пишется строка
   `photos(fileName)`.
4. Миниатюры декодируются с `inSampleSize` под размер ячейки; EXIF-поворот
   применяется вручную (`android.media.ExifInterface`).
5. Удаление: сначала файл, потом строка. Удаление заказа — сначала все его файлы,
   затем заказ (остальное уходит каскадом).

Импорт из галереи копирует поток в свой файл, чтобы оригинал можно было удалить.

## Навигация

`MainActivity` хранит `openOrderId: Long?` в `rememberSaveable`:

- `null` — список;
- число — карточка;
- `BackHandler` сбрасывает состояние, системный back работает предсказуемо;
- процесс смерти переживает только открытый id, данные всегда в базе.

Навигационная библиотека не нужна: два экрана и один параметр. Это меньше кода,
меньше зависимостей и никаких графов.

## Потоки и жизненный цикл

- Room-запросы — на своих executor'ах, UI не блокируется.
- Декодирование фото — `Dispatchers.IO` внутри `produceState`.
- `stateIn(..., SharingStarted.Eagerly)` для секций карточки: запрос стартует сразу
  при создании вьюмодели, а `null` в начальном значении означает «ещё грузимся»,
  а не «пусто». Это убирает ложное «пусто» на первом кадре.
- Для списка — `WhileSubscribed(5_000)`: экран ушёл, поток можно притормозить.

## Обработка ошибок

- Камера может отсутствовать: `launch` обёрнут в `runCatching`, файл удаляется,
  показывается короткий toast.
- Пустой файл после камеры (пользователь передумал) в базу не попадает и удаляется.
- Неизвестный статус из старой версии читается как «Диагностика» — экран не падает.
- Битое фото: миниатюра не декодировалась — показывается заглушка, карточка живёт.
- `FileProvider` настроен только на `files/photos`, наружу не отдаётся ничего лишнего.

## Тестирование

| Уровень | Что проверяем | Инструмент |
| --- | --- | --- |
| JVM | склонения, даты, превью, статусы | JUnit 4 |
| Instrumented | схема SQLite, каскады, DAO, файлы фото, миниатюры | Room in-memory + AndroidX Test |
| Ручной | сценарии на устройстве, скриншоты | TECNO BF7, Android 12 |

Инструментальные тесты используют `Room.inMemoryDatabaseBuilder`, поэтому не трогают
данные пользователя. Файлы фото создаются во временном каталоге приложения и
удаляются в самих тестах.

## Производительность

- Список — `LazyColumn` с ключами по `id`.
- Счётчики в одном запросе.
- Миниатюры 320 px, полноэкранное фото — до 1600 px.
- Никаких тяжёлых библиотек: только AndroidX, Compose, Room, корутины.
- Release APK ~11 МБ; R8 отключён осознанно — приложение маленькое, а правила
  для Room/Compose дороже экономии.

## Безопасность и приватность

- База и фото — во внутреннем каталоге приложения (`files/`), недоступны другим
  приложениям.
- `allowBackup="true"`: данные попадают в системный бэкап Android.
- Разрешений на камеру, хранилище и интернет нет.
- Ключ подписи в репозиторий не попадает (см. `.gitignore`).

## Точки расширения

- Новый статус — значение enum + ключ в базе (миграция не нужна, если не меняется
  набор колонок).
- Новая секция карточки — `SectionCard` + запрос в DAO + поле в `OrderDetailUiState`.
- Экспорт/бэкап — отдельный `io/` пакет: база + `files/photos` в ZIP.
- Напоминания — WorkManager и уведомление по `updatedAt`/дедлайну запчасти.
